The owner's rule in three parts: **a new relationship starts the modal**; **a draft is continued,
invited and published through the modal**; **no Initiator member → resolved through the modal.**

This is the sweep behind it. Every row was rendered — headless Chrome against this branch's dev server
(`BRAND=alignsynch`, `localhost:3001`, 1440×1200) — and the greps cited by line are the code behind what
the render draws. A row that says "obeys" carries a still or a `file:line`; nothing here was judged from
reading code alone.

## What the four fixes change

1. **The list's create door is the modal's door.** `RelationshipCreate` (a server action that copied the
   template into a draft with no session) is `RelationshipStart`: pick a template, navigate into the flow.
   `tests/one-create-path.test.ts` holds the invariant from three sides — one module in the tree writes a
   relationship row (`lib/flow/store.ts`), the list-side action is gone by name, and the band that remains
   renders no form, no hidden field and no action.
2. **The picker offers what the flow accepts.** It read `listMyTemplates` (templates the account
   _authored_), so a member who owns none saw "You have no templates yet" while `/assessment` offered 28
   templates to start from. It now reads the library the flow copies from, filtered to `published` with
   Aspects to copy (`dashboard/relationships/page.tsx:57`).
3. **A draft's Publish goes to the modal**, not to the relationship screen one click before it.
4. **`pnpm flow:e2e` proves the round trip again.** #911 gated stage 5's Send on the walk (a plan and a
   card), so the harness that POSTed the send with neither was failing on the gate rather than on the
   flow — it asserted nothing about the modal. It now writes the method stand-in where the card entry
   belongs (`captureMethodStandIn`), asserts the **refusal** first ("no card, no publish"), then publishes,
   and reaches the fee gate deliberately by clearing the capture (`clearMethodStandIn`) before asserting
   the report stays shut.
