# V1 retirement — the disposition of every `/v1` item

**Issue #478 · disposition only.** This document deletes nothing: no file under `app/(prototype)/v1/**`,
`components/v1/`, `lib/v1/` or `data/v1/` moves or changes in this card. It is the table the follow-up
cohorts are cut from — one row per file, one destination each, and the reason the destination is what it
is. Measured at `fad5f105` (main, 2026-11-03).

## 1. The four destinations

| Destination | Means                                                                                                                                                                                                                                                                                                                                                                |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **release** | Moves out of `/v1` and earns its place in the v2 flow. The row names which of the nine launch criteria it serves (§4) and the v2 consumer that needs it.                                                                                                                                                                                                             |
| **admin**   | Survives as `/admin/console`, behind the same allowlist as `/admin/*` (`requireAdmin`, `ADMIN_EMAILS`), for UI approval only. Not part of the customer product.                                                                                                                                                                                                      |
| **delete**  | Removed with its test and its references. The row names both — the test file and the modules/paths that import or link to it.                                                                                                                                                                                                                                        |
| **defer**   | Refused for now: what it needs before it could ship, and who would own it. **There are zero `defer` rows**, and the reason is the issue's own rule: anything in v1 not required by the nine criteria is a delete candidate, not a defer. Every item here either serves a criterion, is the console, or is already implemented twice — nothing is wanted-but-blocked. |

A `release` lands where its flow lives — behind the shell, in `app/(mainlayout)/**`. None of these
releases exposes anything new: `/v1` is not public either, since `app/(prototype)/layout.tsx` already
gates the whole tree on the demo unlock or a session (`tests/prototype-gate.test.ts`).

### Why this is 118 and the issue says 96

The issue counts 20 routes and 61 components (20 + 61 + 10 + 5 = 96). Those counts were low when the issue
was written, not made low by later work — the same tree measured at the issue's own commit holds the same
files:

```console
$ git ls-tree -r --name-only 35a05c2 -- "app/(prototype)/v1" | wc -l
34
$ git ls-tree -r --name-only 35a05c2 -- "components/v1" | wc -l
69
```

`35a05c2` is the commit the issue's inventory names, and it already carried 34 route files and 69 components.
Counting _route segments with more than one page_ or _components with a test_ would produce smaller numbers,
but neither is the inventory this table needs: every file dies separately. So the table is 118 rows, and the
difference is 14 route files and 8 components the issue's estimate missed. No file merges into another row.

**The honest answer to "which criterion has no implementing surface": none of the nine is wholly absent.**
Four carry a hole, and the hole is narrower than a missing feature:

1. **Criterion 1** — the flow exists; _verified email_ is unproven in the repo.
2. **Criterion 2** — the flow exists; _naming the coach_ has no field anywhere. A launch claim of "name the
   coach" is not shippable as the tree stands.
3. **Criterion 6** — the data exists (sessions and Steps are written); the _screen_ does not. A person can
   complete a session and never see the Steps it derived, which is the one thing the criterion is for.
4. **Criterion 9** — relationships and Gap analytics exist; _templates_ and _users_ are prototype-only.

Nothing in v1 closes 1 or 2. Criterion 9 is closed only by keeping the console — the `admin` rows are the
whole of v1 that survives _because_ a criterion still needs it. v1 closes 6, and that is the only launch
criterion a `release` row serves that v2 cannot serve today. This is also why the release set is four rows
and not forty: the v2 flow was built from v1, and most of v1 is therefore a second copy of something that
already shipped.

## 7. Sequencing, and how the cohorts are sized

Four cards, in this order. The order is not stylistic: three of them break the build if reversed.

| Cohort                | Size    | Contents                                                                                                                                                                                                                                              | Blocked by                                                                  |
| --------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **0 · taxonomy move** | 1 file  | `data/v1/relationship-types.ts` → `data/relationship-types.ts`, all four v2 imports and three tests repointed                                                                                                                                         | nothing                                                                     |
| **1 · admin move**    | 19 rows | the 6 console pages → `app/(mainlayout)/admin/console/**` behind `requireAdmin`; the 7 console components, `relationship-metadata`, `v1-ui`, `lib/v1/admin-console`, `lib/v1/derive` (trimmed), `lib/v1/store` (split or rewired), `data/v1/fixtures` | cohort 0 (fixtures import the taxonomy)                                     |
| **2 · releases**      | 4 rows  | Steps panel into the instance view; demo into `/assessment/demo/[type]`; the pair assertions moved to the v2 report                                                                                                                                   | cohort 0 (taxonomy), and the report projection the demo must render through |
| **3 · deletions**     | 95 rows | the 26 customer pages, the layout and its gate, 58 components, 7 lib modules, 3 fixtures, 9 v1 test files and the references in §6                                                                                                                    | cohorts 1 and 2                                                             |

**Hard constraints**

1. **Cohort 1 before the layout delete.** `app/(prototype)/v1/layout.tsx` is the console's chrome and
   `app/(prototype)/layout.tsx` is its access gate (`tests/prototype-gate.test.ts`). Delete either before the
   console moves and the console is unreachable.
2. **The store split before four deletes.** `lib/v1/chat.ts`, `lib/v1/review.ts`, `data/v1/notifications.ts`
   and `data/v1/plans.ts` are still imported by `lib/v1/store.tsx`. They are `delete` because nothing but a
   dead store slice reads them; the admin-move card must split the store (or rewire it to `lib/db/**`) before
   the deletion cohort touches them.
3. **Cohort 0 before any `data/v1` delete.** Four v2 modules and `data/assessments.ts` import the taxonomy by
   its `data/v1/` path; deleting the directory first is a typecheck failure, not a 404.
4. **The demo repoint lands with the demo release, not with the deletion.** Both live hrefs point into `/v1`
   today; the release is the commit that moves them.

## 8. What this document does not do

- No code moved, renamed or deleted; `README.md` and `AGENTS.md` untouched.
- The follow-up cards (0–3) are created **from** this table, not in this PR.
- It does not decide the console's data source. It records the decision that must be made: keep the
  fixture-seeded store behind the allowlist (small, and honest for UI approval) or rewire the console to
  `lib/db/**` (larger, and the only version where the store and its fixtures can ever be deleted). The
  `admin` rows above are written so either answer leaves them in place.
