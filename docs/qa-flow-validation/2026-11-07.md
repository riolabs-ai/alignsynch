**Question this answers:** does connection → draft → ready → payment → publishing → Gap work today, and where does a
real person first stop?

**Build:** `main` @ `12921914` (v1.5.0), served with `pnpm dev` on `http://localhost:3100`
**Database:** Neon **demo** branch `br-wispy-frog-b43188n8`, endpoint `ep-crimson-truth-b4ppwxrp` (`NEON_BRANCH=demo`)
**Stripe:** test mode — `STRIPE_TEST_SECRET_KEY` (`sk_test_…`), and the provider itself answered `livemode: false`
**Written by:** card `t_b8c9cf50`. No application code, fixture, schema or UI was changed.

> **Verdict in one line:** the two people can connect, answer and read the Gap — but nothing joins the two halves.
> The answer sheet dead-ends at "Waiting for both answers", the accept step has no link (`/accept` is reachable only
> by typing it), and payment is not in the session at all: publishing happens at creation, and the first publish is
> covered by a 14-day trial that never asks for a card.

## Stage table

| #   | Stage            | Verdict                                              | One-line evidence                                                                                                                                                |
| --- | ---------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Connection       | **PASS** (with 3 row-level defects)                  | signup → create → invite link → claim → both seats bound; `relationship.status` stays `draft` on the create path                                                 |
| 2   | Draft            | **ABSENT** (answers) / PARTIAL (relationship config) | no draft save exists for answers: one POST writes the whole sheet; `party.submitted_at` is never written                                                         |
| 3   | Ready            | **ABSENT — first breakpoint**                        | after both sheets are in, the initiator's screen still reads "Waiting for both answers" and offers no next step                                                  |
| 4   | Payment          | **ABSENT from the session**                          | instance/accept/report pages carry no billing link; checkout exists at `/pricing` and inside relationship _publish_, not at completion                           |
| 5   | Publishing + Gap | **PASS for the report, FAIL for the modelled chain** | two acceptances complete the session and both seats read `data-feel-gap="3"` — with no payment, and the relationship row never leaves `draft` on the create path |
| 6   | Blind rule       | **PASS**                                             | before completion neither rendered page carries a Gap attribute or the other party's scores                                                                      |

**First breakpoint that stops the chain: stage 3.** Everything after it (payment, publishing-at-completion) is not
merely unlinked — it does not exist as a state. The Gap _can_ be read, but only because `POST /accepts` is called
directly; a person clicking through the product cannot get there.

## Method

Two real identities were created through the product's own auth endpoint, and the flow was driven over HTTP with two
cookie jars. Commands are in [Reproduction](#reproduction). The two entry points into a relationship were both walked,
because they disagree:

- **the public create path** — `POST /assessment/new` (the form on `/assessment`): creates the relationship, its
  session, the initiator's seat and the invitation in one transaction;
- **the member publish path** — `/dashboard/relationships/[id]` → "Publish and invite", which runs
  `publishRelationship()` (`lib/member/relationships.ts`). Driven by calling that same exported function with the
  actor id the screen passes, because the control is a Next server action with no plain form.

## 1. Connection — PASS, three defects

| Check                            | Result | Evidence                                                                                                                                                      |
| -------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| initiator + counterparty sign up | PASS   | `POST /api/auth/sign-up/email` → 200, two `neon_auth.user` ids                                                                                                |
| create from template             | PASS   | `POST /assessment/new` → 303 `/assessment/instances/5e287f20-…?invite=failed`                                                                                 |
| invitation minted                | PASS   | link on the initiator's screen: `http://localhost:3100/invite/cEKiJ8sGwwPKwtA-16xH3OI4Fd_9codjX9j2v7lD8BM`                                                    |
| invitation email                 | PASS   | `?invite=failed` only for `@example.com` (the provider answers `HTTP 422`); `delivered@resend.dev` and `qa.deliverable@riolabs.ai` both answer `?invite=sent` |
| counterparty claims              | PASS   | `POST /invite/<token>/claim` → 303; `session_invite.claimed_at` set, 2 `party` rows                                                                           |
| both bound as members            | PASS   | `relationship_member` = `[counterparty, initiator]` after the claim                                                                                           |

Row-level defects recorded here (all three are separate findings, none blocks the walk):

1. **`relationship.status` never leaves `draft` on the create path.**
   `{"status":"draft","published_at":null,"purchased_at":"2026-11-07T16:02:38.180Z","initiator_user_id":"abb9da34-…","counterparty_user_id":null}`
   `createInstanceFromTemplate()` inserts the row without a status, so the 0030 default `draft` applies; the claim only
   fires `published → active`, so the claim is a no-op for the status.
2. **`relationship.counterparty_user_id` is never written.** NULL after the claim, and NULL on the member path after
   `published → active`. The seat binds through `party.user_id` + `relationship_member` only.
3. **One relationship, two sessions and two invitations.** Publishing a relationship that `/assessment/new` already
   provisioned inserts a _second_ session (`round` 2) and a _second_ invitation:
   `sessions on this relationship: [{"record_id":"3cb541d2-…","round":1},{"record_id":"member-session-a2ae01e36d","round":2}]`.
   The dashboard also disagrees with the database: it renders **"Draft — Not sent yet — nothing has been invited or
   charged."** while a live invitation link and an open session exist.

## 2. Draft — ABSENT

No answer is ever saved without being submitted.

- `POST …/answers` writes all five `opinion` rows in one statement; there is no partial row set, no draft table and no
  draft endpoint (`grep -rn "draft" lib/flow` returns template/relationship drafts only).
- `party.submitted_at` is **not written by the save** — it is NULL after a submit. The code says so itself
  (`lib/db/admin-instances.ts:97`: "the `party.submitted_at` column is `0011`'s and is unwritten today").
- A party _can_ re-edit before accepting: a second `POST …/answers` answers 303 and overwrites (`money feel` 2 → 4),
  i.e. re-submission is allowed, but it is a full re-submit, not a draft.
- At the **relationship** level a draft does exist: the detail screen carries **"Save the draft"** (→ `pending`) and
  **"Save and mark ready"**, and Aspects stay editable while `draft|pending`. That is configuration, not answers.

## 3. Ready — ABSENT (first breakpoint)

Both parties submitted (10 `opinion` rows, 5 per role). The initiator's own screen, rendered after that moment:

> Connected — you both have a seat; the answers are not both in yet.
> … **Waiting for both answers** — Neither of you can see the other's answers until you have both submitted.
> … **Still to answer: Answer every Aspect** … [Submit/Update answers]
- `instanceStatusOf()` has four values (`awaiting_counterparty`, `answering`, `complete`, `voided`) — there is no
  "both answered, awaiting acceptance" value, so the screen has no state to render.
- No screen links to the accept step. `acceptPath()` (`lib/flow/paths.ts:155`) is referenced only by its own route;
  `grep -rn acceptPath` outside `paths.ts` and `accepts/route.ts` returns nothing, and the rendered instance page
  contains no `/accept` href (`initiator screen has an accept link: false`).
- No column named like readiness exists — the only match anywhere is `relationship.completed_at`.
- Consequence: `POST …/accepts` works (first acceptance keeps the report sealed; the second completes it), so the
  _mechanism_ exists and its only entry point is a URL nobody is given.

This is the breakpoint the sequence stops at. Cards #619 (pay to complete) and #618 (creation wizard) both start from
this moment, and it does not exist yet.

## 4. Payment — ABSENT from the session

| What was tried                                                                  | Result                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| links on the instance / accept / report screens to pricing, billing or checkout | `[]` — none                                                                                                                                                                                                  |
| words "buy / upgrade / pay now / checkout / subscribe" on those screens         | none (the only match was unrelated page chrome)                                                                                                                                                              |
| `/pricing` as the signed-in initiator                                           | 200                                                                                                                                                                                                          |
| `POST /api/billing/checkout {"planId":"basic","interval":"month"}`              | 200`{"url":"https://checkout.stripe.com/c/pay/cs_test_a1YBu6…"}`                                                                                                                                             |
| that session, read back from the provider                                       | `livemode=false`, `status=open`, `success_url=http://localhost:3100/pricing`                                                                                                                                 |
| publish a relationship with no trial used                                       | **publishes with no payment at all** — 14-day trial, `billing_subscription {plan_id:"basic", status:"trialing", provider:"mock"}`                                                                            |
| publish the same account with the clock 20 days on (trial lapsed)               | `MemberCheckoutRequired — a checkout must complete before this relationship can be published: https://checkout.stripe.com/c/pay/cs_test_a1syk7…`; the relationship stayed `draft` and no session was written |

So a payment _can_ be started — in Stripe test mode, from `/pricing` (account subscription, returns to `/pricing`) and
from the relationship **publish** action (returns to the relationship page). It cannot be started from the session, and
the session's completion never consults it. The first relationship anyone creates is covered by a trial; the card's
"plan + payment publishes the assessment" has no implementation.

## 5. Publishing + Gap — PASS for the report, FAIL for the modelled chain

`instanceStatusOf` inputs at completion, read straight from the rows:

```
{"aspect_count":5,"has_counterparty":1,"initiator_answered":5,"counterparty_answered":5,
 "initiator_accepted":1,"counterparty_accepted":1}
```

| Check                                    | Result   | Evidence                                                                 |
| ---------------------------------------- | -------- | ------------------------------------------------------------------------ |
| first acceptance keeps the report sealed | PASS     | 303 → `/accept`, no `data-feel-gap`                                      |
| second acceptance completes              | PASS     | 303 → `/report`                                                          |
| initiator reads the Gap                  | PASS     | `data-aspect="aspect-time-together" data-feel-gap="3" data-wish-gap="2"` |
| counterparty reads the same Gap          | PASS     | identical attributes                                                     |
| a payment caused any of it               | **FAIL** | no checkout was visited; the session completed on two acceptances        |
| the relationship records the completion  | **FAIL** | `{"status":"draft","published_at":null,"completed_at":null,"plan":null}` |

Publishing the _assessment_ to both seats works. Publishing as the product models it — a paid act that opens the report —
does not exist: the report opens on acceptance, and the relationship's own lifecycle (`draft → published → active`) is
driven by the member screen, never by the session.

## 6. Blind rule — PASS

| Check                                   | Result                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| counterparty's screen before completion | no `data-feel-gap`, no `data-wish-gap`                                       |
| initiator's screen before completion    | no `data-feel-gap`, no `data-wish-gap`                                       |
| either page naming the other's score    | none (`{"initiatorSeesCp":false,"cpSeesInitiator":false,"cpInSynch":false}`) |
| report page before completion           | `data-report-gated="true"`, no Gap rows                                      |

`visibleRoles()` is not merely correct as a function — the rendered pages carry nothing to leak.

## Observations that are not stages

- **The demo database is one migration ahead of `main`:** `schema_migrations` lists `0035_form_guard_attempt.sql`
  (applied 2026-11-07T15:11:03Z), which is not in `db/migrations/` on `12921914`. Additive, and the walk was unaffected.
- **Invitation mail works**; `?invite=failed` in the logs is the provider refusing `@example.com`, not a broken sender.
  The `rsm.alignsynch.com` domain answers `verified` / `sending: enabled`.
- **Every row this run created was deleted**: two `@example.com` auth accounts remain (harmless test identities on the
  demo branch), and the demo database is back to its 11 pre-existing `relationship` rows, all `draft`.
